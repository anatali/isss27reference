Capitolo 8: Introduzione all'Analisi del Problema e Modello dell'Architettura Logica

Verso lo sviluppo cooperativo: valutazione delle opzioni progettuali e definizione del modello formale

Goal del Capitolo: Motivare l'importanza fondamentale della fase di analisi del problema nello sviluppo del software. Prima di procedere alla scrittura del codice, è necessario impostare una discussione comparata tra le diverse alternative operative per giungere alla definizione formale di un modello che esprima l'architettura logica del sistema. A questo scopo, vengono introdotti anche gli strumenti di lavoro cooperativo forniti da GitHub.

1. Il Problema dell'Erogazione dei Servizi di Calcolo e Visualizzazione

La classe FSinSeries.java consente sia il calcolo puntuale y = sin(x) sia la generazione di una sequenza di coppie di valori di lunghezza determinata. Nel modello basato su QActor, il microservizio a può adottare diverse strategie per rispondere a una richiesta di valutazione:

  • Generazione aggregata lato server: L'attore a delega interamente il calcolo della sequenza al metodo evalSinPoints e restituisce l'intera struttura dati al chiamante.
  • Gestione interna del ciclo: L'attore a invoca iterativamente il metodo eval (presente anche nella classe FSin.java), calcolando un punto alla volta e prendendosi l'onere di creare la sequenza.
  • Delegazione della visualizzazione: L'attore a assume il compito di visualizzare il grafico delegando un attore specializzato (es. viewer) o un servizio remoto, che restituisce al chiamante una risposta contenente l'URL dell'immagine del grafico:

    Request evalfunvalues : args(MIN, MAX, DX)
    Reply replyaval : done(URL) for evalfunvalues

2. Discussione Comparata e Analisi delle Alternative

Prima di implementare qualsiasi soluzione, l'analista deve condurre una valutazione critica sulle opzioni architetturali disponibili:

Analisi dell'impatto di rete: Calcolo batch vs Visualizzazione incrementale
L'idea che l'attore a calcoli un valore alla volta inviandolo incrementalmente a un servizio remoto di rendering potrebbe rivelarsi inefficace per funzioni semplici come sin(x), in quanto genera un elevato overhead causato dal traffico di messaggi sulla rete.
Contesto applicativo: Il caso della "Mappa Logistica"
Se la funzione da valutare non è una semplice curva trigonometrica ma una "mappa logistica" (implementata nella classe LogisticSeries.java che descrive l'evoluzione temporale di una popolazione), il tempo che intercorre tra due iterazioni successive può essere significativo. In tal caso, la trasmissione e visualizzazione incrementale punto per punto diventa un requisito operativo quasi obbligatorio.

3. Supporto al Lavoro Cooperativo con GitHub

Per condurre in modo trasparente e strutturato la discussione sulle alternative architetturali all'interno di un team, è opportuno avvalersi di strumenti di tracciamento coordinato. GitHub fornisce un ecosistema integrato per coniugare l'avanzamento del codice sorgente con la gestione analitica del progetto.

Concetto: Sviluppo Cooperativo del Software

Metodologia di lavoro strutturata in cui più sviluppatori collaborano sul medesimo repository. Richiede strumenti per sincronizzare le modifiche al codice (Git) e coordinare la pianificazione delle funzionalità (GitHub Projects/Issues), garantendo tracciabilità, riduzione dei conflitti e qualità del software attraverso la revisione tra pari.

Strumenti di lavoro cooperativo
GitHub mette a disposizione funzionalità avanzate per la gestione del flusso metodologico agile, consentendo ai componenti del team di condividere decisioni di analisi prima della scrittura del codice.
Sviluppo cooperativo del software e Sezione Project
La sezione Project di GitHub (accessibile ad esempio nel workspace di progetto History_firstPrj27) permette di organizzare il lavoro di analisi e sviluppo mediante board Kanban, roadmap e tabelle dinamiche. Attraverso la gestione integrata di Issues, Pull Requests e note di lavoro, il team mantiene la completa tracciabilità del processo decisionale.
Concetto: Sezione Project e Viste di Pianificazione

Project è lo strumento di gestione di GitHub che consente di organizzare le attività mediante board Kanban (vista a colonne per rappresentare il flusso di lavoro) o tabelle e roadmap (viste analitiche e temporali). Permette di tracciare l'evoluzione di Issues (task da svolgere), Pull Requests (proposte di modifica al codice) e note operative.

Principio architetturale: Un Project rappresenta un livello di astrazione gestionale. Non contiene codice sorgente ed è del tutto opzionale rispetto al ciclo di vita del repository Git.

E' importante evidenziare che:

  • La sezione Project gestisce il processo di lavoro e non coincide con il codice sorgente del repository.
  • L'adozione di Project è del tutto opzionale, ma costituisce un fattore abilitante primario nei contesti di sviluppo cooperativo distribuiti.

Operatività: Creazione, Collegamento ed Eliminazione di un Project
  • Creazione: Dalla scheda Projects del repository, cliccare su Link a project e selezionare New project. È possibile scegliere un modello come Board (vista Kanban standard a colonne) o Table (vista tabellare a foglio di calcolo) e assegnare un nome (es. LogisticMapPrj).
  • Collegamento (Link a project): Se un progetto viene creato a livello di organizzazione o utente, la funzione Link a project permette di associarlo al repository (es. iss27reference), rendendolo accessibile direttamente dalla pagina del codice.
  • Eliminazione: Accedendo alle impostazioni del Project (Settings), è possibile eliminare definitivamente il tabellone o rimuovere il collegamento col repository senza intaccare la storia dei commit o delle Issue.

5. GitHub Pages

GitHub Pages è un servizio di hosting statico fornito direttamente da GitHub che trasforma i file HTML, CSS, JavaScript e Markdown presenti in un repository in un sito web pubblicamente accessibile via HTTP/HTTPS.

Differenza tra sorgente GitHub e rendering GitHub Pages
Quando si naviga all'interno dell'interfaccia standard del repository su GitHub, l'apertura di un file .html mostra il codice sorgente (il markup raw) per motivi di sicurezza. Tramite GitHub Pages, invece, il file viene interpretato ed eseguito dal browser, consentendo la visualizzazione completa dell'interfaccia grafica, dei fogli di stile, delle formule matematiche (es. MathJax) e il corretto funzionamento di tutti i collegamenti ipertestuali (permalink).

Valore nel Processo Agile e Cooperativo

  • Accessibilità della Documentazione: Consente a committenti, revisori e membri del team di consultare l'analisi dei requisiti e i report architetturali in formato visuale senza dover scaricare il progetto in locale.
  • Preservazione dei Permalink: Tutti i riferimenti incrociati verso sorgenti del repository (es. file .java o .qaktt) o verso altre pagine HTML rimangono pienamente operativi.
  • Automazione CI/CD: Ogni aggiornamento (commit/push) effettuato sul ramo principale rigenera automaticamente la documentazione online.
Operatività: Procedura di Creazione e Configurazione

Esistono due modalità principali per configurare GitHub Pages in base alla struttura delle directory scelta nel repository.

Modalità A: Pubblicazione Nativa tramite cartella '/docs' (Consigliata)
È l'approccio più semplice ed essenziale, ideale per mantenere pulita la radice del repository:
  1. All'interno del repository, creare la cartella denominata docs/.
  2. Inserire i file della documentazione HTML (es. docs/index.html, docs/capitolo9.html).
  3. Effettuare il commit e il push su GitHub:

    git add docs/
    git commit -m "Aggiunta documentazione HTML in docs"
    git push origin main
  4. Nel repository su GitHub, accedere a Settings > Pages.
  5. Alla voce Build and deployment:
    • Impostare Source su Deploy from a branch.
    • Selezionare il ramo main (o il ramo predefinito).
    • Nel menu a tendina delle cartelle, selezionare /docs anziché / (root).
  6. Cliccare su Save.
Modalità B: Cartella Personalizzata (es. 'repoDocs') tramite GitHub Action
Se per convenzione di progetto occorre utilizzare una directory diversa (ad esempio repoDocs):
  1. Creare la cartella repoDocs/ e inserirvi i file HTML.
  2. Creare il file di workflow in .github/workflows/static.yml.
  3. Nel file di workflow, specificare il percorso della cartella nel parametro path: 'repoDocs'.
  4. Nelle impostazioni del repository (Settings > Pages), impostare Source su GitHub Actions.
Operatività: Struttura dell'URL e Verifica del Deploy

Una volta completato il primo deployment (richiede solitamente circa 30-60 secondi), la documentazione sarà pubblicata ed esposta al pubblico al seguente indirizzo:

https://<nome-utente>.github.io/<nome-repository>/<nome-file.html>

Ad esempio, questo file sarà accessibile in rendering diretto all'indirizzo:

https://anatali.github.io/isss27reference/capitolo8.html
